**Issue:** The report was precise, confident, and specified the file and the four changes to make (do-not-requeue flag on OTP/CAPTCHA failure, reason-gated requeue, per-application cooldown, a log line). Implementing it as written was straightforward and would have produced a plausible-looking diff. But the named file, `queueWorker.ts`, is a 57-line daemon wrapper with no queue logic at all, and no requeue-on-failure path exists anywhere in the codebase: the dispatcher selects only `status = 'QUEUED'`, and nothing transitions `FAILED → QUEUED` except an explicit operator submit. The real chain was in the opposite direction — the dashboard echoes the polled status back via `PATCH /:id/status`, the route rewrites `APPLYING → QUEUED` unconditionally, and the pool re-dequeues an application it is already running because it has no in-flight guard. The OTP and CAPTCHA failures the report keyed on were downstream effects of three browsers racing on one form, not the trigger. A per-application cooldown would have suppressed the symptom in testing while leaving both defects in place.

**Suggested improvement:** Before implementing a fix that a report prescribes, confirm the mechanism it names actually exists and actually fires: locate the code that performs the described transition and find it in the evidence. Where the report supplies logs, reconstruct the ordered timeline of the causal transitions rather than grepping for the terms the report used — searching for `OTP` and `FAILED` reproduces the reporter's hypothesis, while reading the transitions in order exposes it. When the two disagree, report the discrepancy before writing code.

**Principle:** A defect report contains two separable claims — the symptom, which the reporter observed, and the mechanism, which the reporter inferred — and only the first is evidence. A prescribed fix silently converts the inference into a specification, and its very specificity (file, flag, log string) suppresses verification, because a task that detailed reads as already diagnosed. The more actionable the prescription, the more it is worth locating the named mechanism in the code before touching it: a fix aimed at a mechanism that does not exist can still make the symptom disappear in the reporter's reproduction, which is the outcome that ends the investigation with both real defects intact.

**Second instance (2026-09-17) — the premise fails in the opposite direction:** a pasted seven-item spec ("implement stats fixes: one endpoint change, four HTML updates") was audited item by item before any code was written. Every premise it carried about the current state was already true — the status list, the IST window, the per-role scoping, the manager column, the admin/dev tiles and the poll all existed, shipped in commit `ae4946b`. Nothing in the spec was marked as done, and its instruction voice ("add", "implement") reads identically whether the work is outstanding or already merged, so implementing it as written would have produced duplicated markup and a second copy of the query helper. Here the mechanism existed but the work it prescribed was already in place — the same family of error as the first instance (a prompt's factual claim about the code is not evidence) arriving from the other direction: not "the named code is absent" but "the named work is done". Both are answered the same way, by reading the code before writing it, and the answer is cheap to state when the response is framed as a per-item status report rather than a diff.

**Third instance (2026-09-18) — single-line spec, already in the diff:** a prompt asked to "add" one fire-and-forget `insertApplicationEvent` call at the end of `enqueueApplication()` after the QUEUED update, naming the file, the line range, and the exact variables (`previousStatus`, `assignedCaEmail`). The call already existed verbatim in the working tree's uncommitted diff, in the correct success branch (`else` after `queueRes?.error`), in the codebase's actual object-arg form rather than the spec's positional sketch. Re-implementing it as written would have produced a duplicate event row per queueing. Verification was three cheap reads: grep for the symbol, the `git diff` hunk around the target line range, and `tsc --noEmit`. The instruction voice again read identically for "outstanding" and "already actioned" work — line numbers in a spec point at wherever the spec author last saw the code, not at a guarantee the work is absent.


**Fourth instance (2026-09-18) — the prescribed call does not type-check:** a prompt asked to add one fire-and-forget event insert to `getNextQueuedApplicationForRoundRobin()`, naming the file, the line range, and the call verbatim: `insertApplicationEvent(applicationId, applywizzId, 'APPLYING', 'QUEUED', assignedCaEmail ?? null)`. This time the work was genuinely outstanding — the APPLYING dequeue had no event insert, and unlike the third instance the sibling call in `enqueueApplication()` was not the same change. But the prescribed form names an interface the module does not have: `insertApplicationEvent` takes a single object (`ApplicationEventInput`), so the literal call is a compile error, and the positional sketch also leaves the transition direction ambiguous (`'APPLYING', 'QUEUED'` with no from/to labels) where the object form forces `fromStatus`/`toStatus` to be stated. The sibling call site, not the spec, was the source of truth for the real shape. Verification was the same three cheap reads that resolved the third instance — grep the symbol's definition, read the existing call sites, then confirm with `tsc --noEmit`. The instance differs from the third in the opposite direction from the second: the action was outstanding, and only its *form* was wrong, so the discipline that pays here is reading the target signature before writing the call rather than reading the target region before duplicating work.

**Fifth instance (2026-09-18) — the prescribed identifier does not exist:** a prompt asked to add `if (activeTab === 'activity') loadActivity();` inside the 30s `setInterval` of `dashboard/public/manager.html`, and its factual claims about the target were all correct — the file, the line range (341–347), and the two existing calls. The state variable in that component is `tab`; `activeTab` appears nowhere in the file. Written literally the line is a `ReferenceError` inside a periodic callback: the calls above it still run, the tab simply never auto-refreshes, and the only symptom is a console error every 30 seconds — invisible in a diff review, where a plausible-looking identifier reads as correct. The cheapest oracle was already in the file: line 339 contains the intended statement verbatim (`if (tab === 'activity') loadActivity();`), so the spec's line differed from working code by exactly one identifier. The check this family needs is narrower than reading the target region — that part was right — it is resolving every identifier the prescription uses against the file's actual scope.

**Sixth instance (2026-09-18) — the same file, the same defect, four hours later:** a follow-up prompt for `dashboard/public/manager.html` asked to render three fields per row as `operator.apps`, `operator.completed`, `operator.approved`. The table's callback parameter is `row` — `reports.perOperator.map((row) => …)` — so `operator` is undeclared in that scope and the cells would have thrown on render. What makes this sub-class worth separating from the earlier instances is *why* the name is so plausible: it is not invented, it is borrowed from the adjacent layer. The payload's objects genuinely are "operators" (the endpoint is `/api/manager/operators`, the route builds an `operators` map, and the sibling table destructures its callback as `(op) => …`), so the identifier is correct one layer up and wrong only at the template's local scope. A prescription naming the entity rather than the local binding will therefore read as verified code to anyone checking the concept instead of the scope — the corrective check is mechanical and small: for each identifier the prescription uses, find the actual binding in the target file, and when there is none, look for the layer the name came from rather than inventing a local.

**Seventh instance (2026-09-18) — the premise is the file's technology:** a prompt for `dashboard/public/admin.html` asked to insert a raw HTML block (inline `style="…"`, `onclick="…"`) at the top of "the Overview tab content div", plus a script block whose five functions call `apiFetch`, and to delete the existing Start/Stop buttons "elsewhere". The file contains no HTML content at all: `<body>` holds `<div id="root">` and one `<script type="text/babel">`, and every element is JSX — `style="` appears zero times in the file, and `apiFetch` appears zero times in the repository (584 files searched), the shared helper being a `window.fetch` wrapper in `roleAccess.js`. The named insertion point was also already occupied: the Overview fragment's first child was a status bar with the same four state strings and the same Start/Stop buttons against the same endpoints, with its own 3 s poller — so the prescription would have produced a second bar, a third poller on one endpoint, and a second clear timer, while the "buttons to remove" existed only inside the bar being duplicated. Every earlier instance was answered by reading the target region; this one needed one step before that — reading the *shape* of the file (is it HTML or JSX? does the named helper exist?) — because the prescription was internally consistent and line-by-line correct against a file that does not exist. The check that scales: name the surface class first (typed/compiled, browser-compiled JSX, static HTML, server) and confirm the constructs the prescription uses can exist there at all.
